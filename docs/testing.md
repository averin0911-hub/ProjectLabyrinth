# Тесты проекта: объяснение с нуля

Тесты — это небольшие функции, которые вызывают код проекта и проверяют
результат. Они находятся в папке `tests` и используют библиотеку `pytest`.
При тестировании обнаружена и исправлена ошибка воспроизводимости `seed`
в генераторе: все случайные выборы теперь используют локальный `rng`.

Начните с разбора ниже: он объясняет тест повторного ввода, который мы
обсуждали. Описание **каждой тестовой функции** с входными данными и ожидаемым
результатом находится в [списке проверок](test-cases.md).

## Что вообще делает тест

У обычного теста три действия:

1. Подготовить пример: например, маленький лабиринт или ответы пользователя.
2. Вызвать проверяемую функцию.
3. Сравнить полученный результат с ожидаемым через `assert`.

```python
maze = Maze([[2, 0, 3]])  # Подготовили лабиринт.
result = BFS(maze).solve()  # Вызвали поиск пути.
assert result["distance"] == 2  # Ожидаем два перехода между клетками.
```

В матрицах `0` — проход, `1` — стена, `2` — старт, `3` — выход.
Координаты записаны как `(строка, столбец)`, нумерация начинается с нуля.
Длина пути — количество переходов: маршрут из трёх клеток имеет длину 2.

`assert условие` означает «проверь, что условие верно». Если неверно, pytest
покажет провал, строку проверки и полученные значения.

## Подробный разбор теста повторного ввода

Проверяем поведение `read_size()` из `main.py`: после ошибочного ввода
функция должна вывести сообщение и снова спросить размер.

Вот тест целиком:

```python
@pytest.mark.parametrize("bad_value", ["abc", "3.5", "-1", "4", str(app.MAX_SIZE + 1)])
def test_read_size_retries_after_bad_input(monkeypatch, capsys, bad_value):
    answers = iter([bad_value, "8"])
    monkeypatch.setattr("builtins.input", lambda prompt: next(answers))

    assert app.read_size("Ширина") == 8
    assert "от 5 до" in capsys.readouterr().out
```

### Откуда берётся `bad_value`

Строка `@pytest.mark.parametrize(...)` запускает эту функцию пять раз.
В первом запуске `bad_value` равен `"abc"`, во втором — `"3.5"`, затем
`"-1"`, `"4"` и строке с числом выше верхней границы. Каждый вариант
проверяется отдельно и получает свой результат в отчёте.

### Где подставляются ответы вместо клавиатуры

```python
answers = iter([bad_value, "8"])
```

Для первого варианта это `iter(["abc", "8"])`. `iter()` создаёт итератор —
объект, который выдаёт подготовленные значения по очереди через `next()`:

```python
answers = iter(["abc", "8"])
next(answers)  # "abc"
next(answers)  # "8"
```

Если вызвать `next()` в третий раз, значения закончатся и возникнет
`StopIteration`. В нашем сценарии должно хватить двух ответов.

Следующая строка подключает эти ответы к программе:

```python
monkeypatch.setattr("builtins.input", lambda prompt: next(answers))
```

`builtins.input` — обычная встроенная функция `input()`. `monkeypatch.setattr`
временно заменяет её другой функцией. Поэтому вызовы `input()` внутри
`read_size()` теперь получают подготовленные ответы, без клавиатуры.
После теста pytest автоматически отменяет замену.

`lambda prompt: next(answers)` — короткая запись функции. Её можно прочитать
как такой код:

```python
def fake_input(prompt):
    return next(answers)

monkeypatch.setattr("builtins.input", fake_input)
```

`prompt` принимает текст приглашения, который программа передаёт в `input()`.
В этой подмене мы его не используем: возвращаем очередной подготовленный ответ.

### Что проверяет первый `assert`

```python
assert app.read_size("Ширина") == 8
```

`app` — имя модуля `main.py` в тестах: в начале файла написано
`import main as app`. Здесь вызывается настоящая `read_size()`.
`"Ширина"` — подпись для запроса, а не ответ пользователя.

При варианте `bad_value = "abc"` происходит такая последовательность:

1. `read_size()` вызывает `input()` и получает `"abc"` из подмены.
2. Преобразовать `"abc"` в целое число нельзя; функция печатает сообщение.
3. Цикл внутри `read_size()` снова вызывает `input()` и получает `"8"`.
4. Функция преобразует строку в число и возвращает `8`.
5. `assert` сравнивает возвращённое значение с числом `8`.

Если функция вернёт строку `"8"`, условие не выполнится: `"8" != 8`.
Если функция перестанет повторять запрос после ошибки, тест также не сможет
успешно получить ожидаемый ответ.

### Что проверяет второй `assert`

```python
assert "от 5 до" in capsys.readouterr().out
```

`capsys` — помощник pytest, который перехватывает вывод, например `print()`.
`readouterr()` забирает накопленный вывод, а `.out` содержит обычный
напечатанный текст. Проверка означает: «в сообщении есть слова `от 5 до`».

Здесь проверяется наличие части сообщения, а не его полный текст и не число
сообщений. Название диапазона должно появиться при ошибочном вводе.

`monkeypatch` и `capsys` вручную создавать не нужно. Pytest видит их имена
в аргументах теста и сам передаёт нужные объекты. Такие помощники называются
**фикстурами**. `bad_value` поступает из списка в `parametrize`.

## Запуск

Выполняйте команды из корня проекта. При первом запуске:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements-dev.txt
python -m pytest -v
```

Если окружение уже настроено, достаточно:

```bash
.venv/bin/python -m pytest -v
```

Можно запустить только один файл или один тест:

```bash
.venv/bin/python -m pytest tests/test_maze.py -v
.venv/bin/python -m pytest tests/test_algorithms.py::test_no_path -v
```

## Что находится в файлах

| Файл | Что проверяет |
| --- | --- |
| `tests/test_maze.py` | Размеры, клетки, границы, соседей, старт и выход, пустое поле |
| `tests/test_generation.py` | Размеры сгенерированных полей, внешние стены, маркеры, связность проходов и `seed` |
| `tests/test_algorithms.py` | Кратчайшие пути, ошибки, правильность маршрута, повторные запуски, обёртки и эвристику A* |
| `tests/test_main.py` | Ввод размеров, печать, замер времени, сравнение алгоритмов и пункты меню |

Подробности по всем функциям: [модель](test-cases.md#модель-лабиринта-test_mazepy),
[генератор](test-cases.md#генератор-test_generationpy),
[алгоритмы](test-cases.md#алгоритмы-test_algorithmspy),
[консоль](test-cases.md#консоль-test_mainpy).

Для алгоритмов используются небольшие матрицы с заранее известным ответом.
Например, в поле `[[2, 1, 3], [0, 0, 0]]` путь обходит стену и занимает
4 шага. Если коротких путей несколько, проверяется длина и допустимость
маршрута: точный список координат может различаться.

## Как читать тест

Пример из проверки размеров:

```python
def test_size_and_cell_access():
    maze = Maze([[2, 1, 0], [0, 0, 3]])  # Создаём поле из 2 строк и 3 столбцов.

    assert maze.rows == 2               # Проверяем количество строк.
    assert maze.cols == 3               # Проверяем количество столбцов.
    assert maze[0, 1] == 1              # Проверяем клетку со стеной.
    assert maze[1, 2] == 3              # Проверяем клетку с выходом.
```

- `assert` проверяет условие. Если оно неверно, тест не проходит.
- `pytest.raises(ValueError)` проверяет, что неправильный ввод вызывает ошибку.
- `@pytest.mark.parametrize(...)` запускает один тест с несколькими наборами
  данных. Например, проверка границ повторяется для разных координат.
- `solver_class` — общая фикстура: pytest передаёт в тест по очереди классы
  BFS, двунаправленного BFS, Дейкстры и A*. Поэтому один тест проверяет
  сразу четыре алгоритма, без копирования его кода.
- `monkeypatch` временно заменяет функцию. В консольных тестах он подставляет
  ответы вместо ручного ввода и заданные показания вместо настоящих часов.
  После каждого теста замены автоматически отменяются.
- `capsys` сохраняет напечатанный текст, чтобы тест мог его проверить.

### Другие записи, которые встречаются в тестах

| Запись | Как прочитать | Для чего используется |
| --- | --- | --- |
| `assert value is None` | Значение отсутствует | Проверка отсутствующего старта или результата поиска |
| `assert result is expected` | Это один и тот же объект | Проверка, что замер времени вернул результат алгоритма без замены |
| `assert not condition` | Условие должно быть ложным | Клетка за границей не должна быть проходимой |
| `with pytest.raises(ValueError):` | Внутри блока должна возникнуть ошибка `ValueError` | Проверка недопустимых координат или размеров |
| `match="Выход не найден"` | В тексте ошибки должна встретиться эта фраза | Проверка причины ошибки |
| `set(cells)` | Множество уникальных клеток | Сравнение соседей без учёта порядка, поиск повторов |
| `len(path)` | Количество клеток в списке | Проверка длины маршрута |
| `all(условие for ... in ...)` | Условие верно для каждого элемента | Проверка, что все клетки границы — стены |
| `[row[:] for row in grid]` | Скопировать каждую строку матрицы | Сохранить поле до вызова или дать алгоритмам отдельные поля |
| `zip(path, path[1:])` | Перебирать соседние пары клеток пути | Проверка каждого перехода маршрута |
| `*args` | Собрать переданные аргументы в кортеж | Записать, с какими аргументами вызвали подменённую функцию |
| `calls.append(...)` | Добавить запись о вызове в список | Проверить число вызовов и переданные данные |

### Почему в тестах времени есть выдуманные часы

В `test_measure_algorithm_converts_seconds_to_milliseconds` часы подменены:
первое показание — `10.0`, второе — `10.125` секунды. Разница равна
`0.125` секунды, то есть `125` миллисекунд. Именно этот ответ мы ожидаем.
Тест не ждёт 125 миллисекунд и не требует от алгоритма конкретной скорости.

В `test_compare_calls_each_algorithm_once_on_same_maze` подменён весь замер.
Числа `12`, `23`, `34.5` — специально заданные значения для проверки таблицы:
длина, число обработанных клеток и время. Это не результаты настоящего поиска
на поле из двух клеток. Сама работа алгоритмов проверяется в другом файле.

Чтобы добавить свою проверку, создайте функцию с именем `test_...` в одном
из файлов: подготовьте маленький пример, вызовите нужную функцию и сравните
ответ с ожидаемым через `assert`.

## Что означает результат запуска

При проверке 7 ноября 2026 года получено:

```text
141 passed
```

`passed` означает успешные проверки. Число включает отдельные варианты
параметризованных тестов.

Раньше результат был `140 passed, 1 xfailed`. `xfailed` означал выполненную
проверку с заранее известной ошибкой: генератор использовал глобальный
`random.randint()`, хотя для остальных случайных выборов создавал собственный
`rng = random.Random(seed)`. Поэтому одинаковый `seed` не гарантировал
одинакового поля.

Исправление в `core/maze.py`: вызов `random.randint(0, 1)` заменён на
`rng.randint(0, 1)`. Теперь все случайные решения генератора зависят от одного
`seed`. С теста убрана отметка ожидаемой ошибки `xfail`: он проходит как обычный.

Тест временно задаёт разные ответы глобальному `random.randint()` и проверяет,
что матрица, старт и выход остаются одинаковыми при одном `seed`. Он сохраняется,
чтобы эта ошибка не вернулась при следующих изменениях кода.

Запустить только эту проверку:

```bash
.venv/bin/python -m pytest tests/test_generation.py::test_same_seed_does_not_depend_on_global_random -v
```

DFS и графический интерфейс пока не реализованы и в этот набор не входят.
Скорость работы на больших лабиринтах здесь не оценивается: тест времени
проверяет перевод секунд в миллисекунды и порядок вызовов с подменёнными часами.
